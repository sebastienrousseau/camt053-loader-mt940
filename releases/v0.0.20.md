# camt053-loader-mt940 v0.0.20

Housekeeping. No behaviour changes: the parser is byte-for-byte the one
shipped in 0.0.18.

## Why the number jumped

The `camt053` suite ships **one version number across all six packages**
by policy, and it had drifted to six different ones:

| package | was |
| :--- | :--- |
| `camt053` | 0.0.18 |
| `camt053-lsp` | 0.0.18 |
| `camt053-mcp` | 0.0.19 |
| `camt053-loader-mt940` | 0.0.18 |
| `camt053-loader-mt942` | 0.0.16 |
| `camt053-writer-xlsx` | 0.0.16 |

Nothing breaks when that happens, which is exactly the problem. A member
left a release behind still installs, still imports, and still passes its
own tests. The only thing that disagrees is the index, and only if
somebody goes and looks.

All six now sit on **0.0.20**.

## What this adds

**A scheduled drift check.** `scripts/check_suite_consistency.py` runs
daily and compares this tree, and every published member of the suite,
against PyPI. It exits non-zero when they disagree, so the schedule
becomes a notification rather than a report nobody opens. It catches two
things: a member left behind, and a version bumped in the tree but never
tagged — the latter has happened three times elsewhere in this suite,
each time stranding a security floor that reached nobody.

**A refreshed conformance gate.** `tests/test_suite_conformance.py` is
updated to the current canonical copy, picking up the invariants added
since this repository last took it.

## Upgrading

Nothing to do. `pip install --upgrade camt053-loader-mt940` and the
parser behaves exactly as it did in 0.0.18.

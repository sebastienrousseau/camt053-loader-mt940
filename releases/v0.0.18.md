# camt053-loader-mt940 v0.0.18

**Breaking.** A statement whose `:25:` does not identify an account is now
rejected rather than parsed into an account of `None`.

## What changed

`parse_mt940` refuses three shapes it previously accepted: `:25:` absent,
`:25:` present but empty, and `:25:BIC/` naming a servicer with no account
number. Each produced a `ParsedDocument` whose entries belonged to no
account.

That output was invalid on both sides of the bridge. `:25:` is mandatory
under the SWIFT MT940 specification, and `<Stmt><Acct>` is `[1..1]` in the
camt.053 model this loader exists to produce. It also had no business use: a
statement with no account cannot be routed or booked.

The practical cost was the worse one. The `None` account pushed a defensive
`if account is None` onto every downstream consumer, and anyone following the
quick start into `document.statements[0].account.iban` met an
`AttributeError` on `NoneType` inside their own code instead of a clear
message at the parse boundary.

## The escape hatch

```python
document = parse_mt940(payload, strict=False)
```

For legacy feeds where the account is known from the filename or the SFTP
folder. Keyword-only, so a stray positional argument cannot silently
reinstate the old behaviour.

## The new exception

`MissingMandatoryFieldError`, exported from the package, subclassing
`ValueError` so existing `except ValueError` handlers keep working. It
carries `.tag` and `.description`.

## Known gap

`:28C:`, `:60F:` and `:62F:` are equally mandatory and still accepted when
absent. `strict` does not yet cover them.

## Verification

79 tests pass at 100% branch coverage. The new rule was mutation-tested: the
first implementation read `statement.account is not None`, which is true
whether or not `:25:` was ever present — it passed its own tests while
rejecting nothing.

## Migration

Pass `strict=False` and attach the account yourself, or fix the source.
